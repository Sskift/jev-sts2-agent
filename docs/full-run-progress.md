# 整局实测进展

更新：2026-09-20。目标是同一局标准游戏经过三幕、击败最终 Boss、进入正式胜利结算；当前尚未达到该目标。

当前实现：Node + 游戏内 C# 模组，Jev 选择有策略取舍的完整动作。唯一合法动作和已经选择跳过后的流程推进由代码处理。普通奖励不再结束循环。已加入购买卡牌/遗物/药水、商店删牌、奖励领取/选牌/跳过、遗物和组合选择、水晶球候选及战斗外可用药水。

上下文采用完整 JSON 请求，不依赖 Jev 跨调用记忆。保留当前战斗历史、出牌时的规则和相关资源变化；已结束战斗的战术动作留在本地，跨房间携带构筑与资源变化。重复说明和卡牌状态可在单个请求内去重。上游公布单个问题的状态与问题合计上限为 32k tokens；本地字节限制仅为初筛，实际 token 使用记录在 API 响应中。

第一局 `run-1789840836`（Ironclad、标准模式、进阶 0）在第一幕第 9 层正式失败。第二局 `run-1789842971` 在第 12 层失败，经过精英、休息、商店和附魔。第三局 `run-1789844801` 在第一幕第 17 层 Boss 战失败，敌人剩余 37 生命。第四局 `run-1789846626` 已击败第一幕 Boss 仪式兽，领取奖励并正常进入第二幕；经过古代人选择、事件强化和普通战斗，目前在第 25 层继续同一局，尚未通关。日志按时间保存在 `run-artifacts/`。

实测修复包括：空数组被上游省略、药水使用历史说明空引用、抽牌历史说明误写为弃牌、奖励命令名与注释不一致、重复跳过卡牌奖励、结算胜利字段读取错误、部分选择/商店说明未展开数字。针对目标的伤害使用游戏的预览计算，原始规则文字中的基础伤害与实际预览值明确区分。

网格选牌曾未返回卡牌列表，三次使用截图核对列表后由 Jev 选牌，再用 Computer Use 执行对应点击；没有由助手代替 Jev 选择。模组增加实际卡牌网格后备读取，第二局附魔界面已正常返回卡牌。附魔预览另有隐藏确认按钮误点问题，本次用 Computer Use 完成 Jev 已选卡牌的确认；修复版只点击可见且启用的确认按钮，并返回附魔规则。游戏仅在战斗或事件已结束后正常关闭、部署更新，再正常继续同一存档，没有重置战斗或编辑存档。

第二局的明确决策错误是低血量时忽略了致死攻击。现给候选添加单步生存估算：当前意图的总伤害、执行后的能量和格挡、若立刻结束回合的剩余生命，以及“滑溜”等已知伤害上限。它不是完整战斗模拟，不预测抽牌、触发效果或后续行动，也不代替 Jev 选择。对失败前局面进行无游戏操作的 Jev 回放，模型改选了能保命的“耸肩无视”（75%），后续仍需整局验证。

第三局还暴露出两个策略问题：对有次数限制的伤害上限浪费大攻击，以及临近 Boss、没有后续商店时囤积金币。现补充便宜攻击消耗上限后的已知手牌伤害计算，并明确商店卡牌能量、花费、剩余金币和后续商店距离。对当时商店做无游戏操作回放，Jev 改选购买打折的“狂怒”（59%）。这些是局面回放结果，不能当作胜率结论。

长战斗的上下文整理保留当前事件顺序和所有卡牌规则，去掉地图已有的成功行走记录、成功命令的回显、重复的格挡/能量观察及过时的地图分支。历史表格共享固定字段；当前请求仍自给自足。第四局 Boss 战曾因 60,187 字节超限停在决策前，整理后降至 56,845 字节，继续同一战斗并获胜。

第二幕多敌人战斗再次触发上下文门槛，已去掉每个候选中重复的手牌规则和敌人说明，通过索引关联同一 JSON 的完整状态。更早各幕的资源与构筑变化按楼层范围汇总，完整中间记录保留本地。一次无游戏操作的容量测量中，66,970 字节完整请求成功，实际输入 32,114 tokens，因此将本地字节门槛从 60 KB 调整为 70 KB；这不是服务端 token 限制，服务端拒绝会在动作前停止。

当前工程检查：81 项 Node 测试通过；兼容模组使用本机 SDK 8 Roslyn 与游戏程序集编译成功。当前构建标签 `0.111.0-context.2`。实测已确认附魔规则、附魔确认、伤害预览、易伤数值展开和第一幕至第二幕过渡。第二幕地图处正常退出部署规则文字的连续能量图标计数修复，安装 DLL 与构建哈希一致。命名管道连接失败时区分“尚未发送”和“结果未知”，前者重新观察后决策，后者保留待核对状态；Windows 短暂文件共享冲突会重试原子记忆写入。后续流程仍需整局验证，不能据此声称已经通关。
