# Jev 决策上下文与 JSON 协议

更新：2026-09-20。完整上下文已接入真实 Jev 调用与游戏模组，正在持续进行整局测试；最新结果见[整局进展](full-run-progress.md)。本项目直接在 `master` 开发提交；仅外部 CLI 模组的改动考虑上游 PR。

## 调研结论：每个请求自行携带上下文

TypeSafe 当前公开 HTTP 契约只有 `model`、`state`、`questions`，SDK 的 `SystemOneRequestPayload` 也是这一结构，没有 conversation/session ID、previous response ID 或增量更新接口。官方 State 文档要求把相关记录、历史对话等放进当前 `state`。据此，本系统按**独立请求、客户端持有记忆**实现，不能只发送 diff 并假定 Jev 记得上一次。服务内部可能存在的性能缓存也不能当作可用会话记忆。

来源：[HTTP API](https://docs.typesafe.ai/api)、[State](https://docs.typesafe.ai/concepts/state)、[SDK 请求契约](https://docs.typesafe.ai/sdk/javascript/api/interfaces/SystemOneRequestPayload)，本次直接读取实时官方 Markdown。

官方当前列出 `jev-latest → jev-1.13.0`；整个请求 64k token，**state + 最长单题 32k token**，当前单题选择受后者约束。公开吞吐限制为 250,000 token/s、1,200 请求/分钟，官方明确说明会动态调整。系统逐步执行，不为消耗吞吐并行执行相互依赖的游戏动作。[Models](https://docs.typesafe.ai/models)

官方同时提醒 Jev 对精确计算、过多无关内容及多层间接引用存在弱点。因此路线可达性、距离和数量范围由代码计算；上下文保留相关原始事实，去重不改变事实。卡牌和效果规则仍以 JSON 内文字字段表达，数量、状态、关系和动作参数使用明确类型。游戏当前语言的文本照实保留，英文稳定 ID 作为辅助；没有声称将中文规则自动翻译成英文。[已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 协议和数据范围

协议版本：`sts2.decision.v1`。正式定义是 [JSON Schema](../schemas/decision-context.v1.schema.json)，完整可检查请求为[合成示例](examples/decision-context.v1.json)。示例的 `offline-*` 局面来自测试夹具，不是真实游戏观测。

| 字段 | 内容 |
|---|---|
| `objective` | 完成同一局三幕和最终 Boss；正式胜利结算为执行终点 |
| `screen` / `in_combat` | 当前界面与是否存在底层战斗；选牌覆盖层也保留战斗 |
| `run` | 本局/战斗标识、幕/层、进阶难度、模式与修改规则 |
| `player` / `resources` | HP、最大 HP、金币、能量、格挡、遗物效果/计数、药水及容量、能力、角色资源和宠物等 |
| `deck` | 永久牌组：每张牌的规则、费用、升级、关键词、附魔/负面附着；与战斗各牌堆分开 |
| `map` | 当前及后续所有可见节点和边、经过节点的类型、Boss 标识；合法下一节点及路线统计。已无法返回的过去分支留在本地日志 |
| `combat` | 回合、行动阶段、完整手牌/抽牌堆/弃牌堆/消耗堆/正在结算的牌、敌人 HP/格挡/能力/可见意图及战斗历史 |
| `screen_state` | 当前事件、奖励、商店或选牌界面的原始信息和选择约束 |
| `rules` | 当前卡牌、遗物和药水相关的游戏悬浮提示说明 |
| `memory` | 本局观察以来的行动、实际响应、出牌当时的牌状态与玩家资源/构筑变化 |
| `information` | 数据来源、明确未知的信息、合并规则和提取错误 |
| `legal_actions` | 本实现支持且当前状态允许的完整选项：稳定 `action_id`、准确命令参数和说明 |

`legal_actions` 和 Jev `questions.next_action.criteria` 的 ID 一一对应。模型只返回已提供的 ID，代码执行该选项的原始命令；模型不能生成新命令或修改参数。包含牌的具体副本、目标和可用药水，也覆盖选路、事件、奖励领取与跳过、商店购买与删牌、休息和多种选牌界面。执行范围仍以候选生成器为准，罕见特殊机制通过实测逐项补齐。

战斗候选包含简单数值估算，包括执行后的能量、当前意图伤害、格挡和若立即结束回合的剩余生命；同时计算剩余手牌在当前费用下能达到的首击伤害。它不是完整战斗模拟，抽牌、触发效果、复活、费用和能力后续变化可能使结果不同。原始卡牌和能力规则同时提供，由 Jev 作策略判断。

## 同一时点的模组上下文

`decision-context.patch` 与 `context/DecisionContextBuilder.cs` 在兼容补丁后应用。`state` 的同一次游戏主线程调用取得界面、玩家、永久牌组、当前幕地图及战斗历史，避免分别查询后拼接来自不同时点的数据。各观察显式发送 `include_pile_details:true`。

模组保留牌堆的完整描述，补充卡牌实例标识、升级层数、星星费用、附魔/负面附着效果及合法目标；保留药水使用条件和合法目标。实例 ID 为随机不透明标识，避免按抽牌堆枚举顺序编号而泄露顺序。显示能力的 `Amount` 模板格式化失败曾导致整个能力被上游跳过；补丁绑定实际 Amount 并保留失败诊断。

检查玩家、牌组、各牌堆、敌人和能力数量，以及必需规则文本；提取失败或数组缺失不能伪装为空集合继续决策。旧模组没有 `decision_context.schema_version:1` 时，Agent 明确停止并提示需要安装新构建，不退回信息缺失模式。菜单和角色选择尚未进入 run 时允许 run/deck/combat 为 null。

人类未知的信息不作为模型事实：不读取 RNG、种子、未来事件/战斗表，不提供隐藏抽牌顺序或敌人内部下一招状态机标签。抽牌堆作为无序多重集合发送；弃牌堆、消耗堆和行动历史保留观察顺序。已发生的选择与卡牌效果仍在历史中，模型可据此推断玩家能够知道的局部信息。问号节点不假定安全；未揭示的第二个 Boss 及未来幕内容仍未知。

路线统计使用图遍历与动态规划，不枚举指数数量的完整路径。每个合法下一节点提供最近营火/商店等距离、可达节点数、到已知终点的各类房间数量上下界；不同类型的上下界可能来自不同分支，协议明确说明，避免把它们拼成一条不存在的路线。实际合法移动来自地图 UI 状态，不能用图邻接替代遗物等规则计算出的可选节点。

## 记忆、完整性与容量

每次 API 调用都发送独立完整 JSON。`run-artifacts/mod-memory.json` 原子写入行动和观察记录，Agent 进程重启后可继续同一个仍在运行的游戏 run；不再截成最近三步。通过模组 run ID 隔离不同局，错误或超时留下未确认动作，重启也不自动重放。

本局身份使用游戏保存的起始时间，不依赖内存对象地址，正常重启游戏和读取同一存档后仍能关联已有记忆。战斗身份和卡牌实例独立标识；新局会清空旧局的决策记忆。实测部署更新只在战斗结束后正常退出，不重置战斗或编辑存档。

当前状态是权威事实，历史变化记录会注明可能来自 Agent、游戏或人工操作，不把相关性当因果。返回决策后重读完整状态；永久卡组、资源、任一牌堆、事件效果等改变都会丢弃旧选择。只有采样时间和抽牌堆的随机展示顺序被忽略。

请求先经 Ajv 8.20.0 编译的 JSON Schema 检查，再校验跨字段一致性和选项唯一性。Ajv 只在 Node 进程中加载，不增加服务或后台进程。超过 **30,000 UTF-8 字节**时进行整理，默认本地门槛为 **70,000 字节**；字节数不是 token 数，不能保证请求满足服务端窗口。真实 66,970 字节请求返回 32,114 个输入 tokens；原先 60 KB 门槛会提前挡住这份合法请求。服务端拒绝仍会在游戏动作前停止。

当前战斗保留游戏事件和出牌状态；本幕已结束房间按房间保留构筑与资源净变化，较早各幕合并为带楼层范围的净变化摘要，战略选择和事件结果仍列出。完整中间快照继续保存在本地。重复的能量/格挡观察用当前值和游戏历史表示。整理采用：

1. 重复长文本改为 `text_ref`，其全部原文在**同一请求**的 `text_dictionary` 中。
2. 历史记录改为 `record_table_v1`：`layouts` 是字段名数组，`rows` 每行第一个值是布局编号，其余是按该字段顺序排列的原值。保留每一条事件、字段缺失差异和时间顺序。
3. 重复字段较多时可使用 `record_table_v2`：布局的 `constants` 保存共享值，`fields` 指定每行其余数值对应的字段。每行仍以布局编号开头。两种表格编码均可完整还原事件；代码选择体积更小的表达。
4. 历史卡组变化中的卡牌若与当前永久卡组某一组完全一致，用 `deck_group_index` 引用同一请求的 `deck.cards[index].card`；历史版本有任何差异都会保留自身规则。

战斗动作通过 `card_hand_index` 和 `target_combat_id` 关联同一 JSON 中的手牌与敌人，携带完整命令和简短数值提示，不逐项复制完整卡牌规则。策略指令按战斗/非战斗场景提供，减少无关的提示文字。

仍超限就明确停止并保留诊断，不悄悄截断卡牌、规则和当前战斗事件。长 Boss 战已实际触发过门槛，后续通过消除重复字段和无关的过去地图分支继续。模型返回后记录实际 `usage.input_tokens`/`output_tokens`、模型版本和时延；请求前保存精确 `jev-request.json` 与字节/候选指标。离线测试不能产生真实 token 用量或测量服务吞吐。

## 验证与下一阶段

`npm test` 覆盖地图选路所需玩家/卡组信息、完整牌堆与战斗历史、覆盖层、规则缺失、旧模组拒绝、牌副本与合法目标、药水、副作用前的状态变化、记忆持久化/隔离、未确认动作、独立请求完整性、Schema 和压缩可逆性。

上下文最初版本的 **64/64 测试**、依赖检查和构建哈希保存在[历史验证记录](evidence/2026-09-20/context-validation.json)。后续测试与实机结果持续更新在[整局进展](full-run-progress.md)。

`npm run context:benchmark` 是纯离线合成基准。已保存[本机记录](evidence/2026-09-20/context-benchmark.json)：30 张永久牌、55 地图节点、100 条游戏事件、12 条 Agent 动作的案例经无损整理从 40,638 降至 27,531 字节；准备阶段中位约 1.91 ms、P95 约 3.17 ms。另一个 55 节点双分支地图案例约 9.2 KB。RSS 记录包含整个 Node/Ajv 进程，不含游戏；这些数字不是实机采集耗时、Jev 网络延迟或策略胜率。

当前模组 `0.111.0-context.2` 已部署并用于整局测试。构建产物在 `mods/sts2-cli-compat/out-context/`。`npm run context:preview` 可只读检查当前完整 JSON，不调用 Jev、不发送游戏动作，也不修改记忆。`npm start` 默认连续运行至正式结算、明确错误或步数上限。

真实长战斗也出现过 65,104 字节即被服务端拒绝的情况，说明字节门槛不能当作 token 保证。历史表布局现在还会按相同字段集合和事件类型共享实际恒定值，保持原有 record_table_v2 格式并通过逐项还原测试；该局面整理到 60,336 字节、31,165 输入 tokens 后成功续玩。
