## 信息组织

1. 游戏内 C# 模组读取当前状态、原生效果、目标预览和合法选项。Node 校验完整性，不覆盖实时数值。
2. 本地保存 [Spire Codex](https://spire-codex.com/developers) Beta v0.111.0 的英文 JSON：595 张牌、298 件遗物、64 种药水、265 种能力、66 个事件，以及怪物、遭遇、关键词、附魔、负面附着等，共 14 类。按 ID 查询并补全关联规则，不需要常驻服务或每步网络查询。
3. `rule_reference` 从当前永久卡组、各牌堆、玩家/敌人状态、商店与候选选择取条目，沿生成牌、能力、关键词等关系展开。`related_rules` 将条目直接关联到对应解释，例如 Speed Potion → Dexterity → 游戏原生的“提升卡牌获得的格挡”。不会展开所有随机牌池。
4. `decision_brief` 放置当前生命、能量、格挡，以及同一战斗最近四个已确认动作、打出时的牌面规则和实际资源变化。新的动作记录保存命令前后的有限快照；早期日志没有这些快照时明确为未知。完整游戏历史继续保留，摘要不冒充模型的长期记忆。
5. 每个 Choice 选项直接附带有限算术：剩余能量、格挡、目标伤害、立刻结束时的生命，以及在既定费用下可支付的后续攻击。条件估算与已观察事实分开，不把未知触发和未来抽牌当作确定结果。
6. 战斗使用回合计划：Jev 先选择本回合目标，再选择主要收益、前置准备及选牌/保留意图，形成带资源预留的有序序列。计划生成后，比较相邻顺序调整、单动作替换、两张动作换成一张未用动作，以及补入一张当前可用牌/药水的完整序列，最多两轮；便宜替换与用剩余能量追加动作可以一起比较。两换一和便宜替换加后续动作各限每轮 96 个。这是有限局部比较，不是穷举求解。拿牌/购买等选择仍使用既有独立增益评分。
7. 代码按实例逐条执行同一计划，重新匹配当前合法候选并在发指令前重读状态。普通出牌后继续既定顺序；抽牌、费用/能力/意图变化、敌人死亡、选牌结果或外部变化触发 Jev 复核。它可以保留原计划、只修改未执行部分，或明确改变目标。

目标类别、候选生成、局部比较范围和执行约束由代码定义；Jev 在这些边界内选择目标和有序方案。当前还不是任意生成并验证多回合策略的求解器，也不把 Wiki 中可能出现的后续事件页面当作本局当前可执行按钮。

## 回合计划与执行

`turn_plan` 以 run/combat/turn 为作用域，保存目标、revision、ordered_steps、cursor、已确认动作、资源预留、保留给自动出牌的卡和待复核原因。准备动作可以绑定 `beneficiary_instance_id`；例如先 Armaments、选择指定攻击升级、再打出那张攻击。`turn_planning` 是当前问题的规划阶段，明确指出拟执行步骤尚未发生，实际 `combat` 不被改写为猜测的未来状态。

同回合的普通连续出牌不再次询问独立的下一张牌。模型仍会在构建计划时回答多个窄问题，但这些问题共同组成一份在首个命令前已确定的序列。每次复核都有完整当前状态、原目标、已确认动作和剩余计划。执行结果不明时不推进 cursor，不重发命令；跨回合/战斗/新局不继承过期计划。

在真正结束回合之前，Jev 再检查一次实际剩余手牌、能量、药水和威胁；原有目标保持在上下文中。若发现有用的继续动作，创建同目标的短续接段，观察其结果后再规划余下部分。这是结束阶段的复核，普通计划中相邻的出牌仍直接沿用顺序。条件估算可能漏掉免费抽牌的价值，因此不能仅凭预先选中的 end_turn 就直接交出回合。

context.14 在手牌提供 `upgrade_preview`，在手牌选择的 selectable/selected 卡上提供同源实例标识。升级预览来自未注册副本，不改变真实卡；它是当前、未指定目标的可查看升级展示，不包括执行升级/出牌的触发结果。复制前在另一个 staging 副本清空事件字段，避免原生深克隆附魔时通知活牌的订阅者；未知反射布局失败关闭。旧模组缺少选择实例标识时，只在同 ID 唯一时绑定指定升级对象。

第二十局第 6 层已实机验证完整升级依赖：Armaments 规划指定 Defend 实例 `67194354366d40a3b86c2cfdbef3333a`，HAND_SELECT 由计划直接选择同一实例；确认后同实例变为 Defend+、实际 Block 从 5 变 8，后续打出使已有 5 Block 变为 13，再打 Strike。选牌没有新独立模型选择；升级后复核保留本回合防御目标。见[实际状态与动作摘要](evidence/2026-09-20/live-upgrade-followthrough.json)。这验证了准备、选牌与使用的衔接，不证明该局面选择最优或整局胜率改善。

条件算术单独列出能量、当前伤害/格挡预览和未模拟效果。支持已核实的 Stomp 每张先行 Attack 减 1 费，Rage 的一次一张攻击触发；不把所有触发都当作可预测。Orichalcum 不在中间步骤提前生效，旧 X 费次数不用于能量已改变后的伤害保证。需要完整模拟的能力、升级、药水、抽牌和目标修正仍以实际观察为准。

第二十一局发现已生效 Plating 的规则完整可读，但旧的结束回合估算遗漏了它，使原始能力与派生数字不一致。现在把 `block_after_card` / 方案的 `block` 留给当前格挡与立即收益；`end_turn_block_gains` 列明来源、数量和触发时机，`block_including_end_turn_gains` 用于结束回合的有限伤害计算。已核对本机 v0.111.0：Orichalcum 先检查零格挡，Plating 后获得当前层数的 Unpowered 格挡，因此无立即格挡时两者可以叠加，不额外应用敏捷/脆弱，也不在下一张牌之前重复获得。

第二十一局第一幕 Boss 首回合的实际成对请求暴露了药水比较偏差：有无 Strength Potion 的方案都显示 27 伤害，因为算术忽略药水效果，模型最终移除了药水。原请求已经有 Strength / Dexterity 的关联规则，问题并非完全没有解释。现在数量、持续时间、影响对象和先后关系由 `potion_effects` 明确提供；数字移入 `known_effects_only`，未模拟效果单列，不能把相同的局部基线视为相同最终收益。原始状态与当时历史的只读完整管线回放改为 Dexterity Potion → Defend → Strength Potion → Strike → Strike（21 次模型请求），说明开始考虑持续增益；它仍在非攻击回合加入多余 Defend，不能据此宣称整体方案最优。回放没有发送游戏命令，记录在 `temp/potion-timing-replay/result.json`。

## 事实与边界

地图在完整节点和边、分支数量范围之外，提供每个当前分支的一条 `minimum_elite_route_example`：沿真实连接通往 Boss 的最少已知精英路线。它让恢复、普通战斗和精英的实际先后关系直接可读；同等精英数量下只给一条示例，并非所有取舍的最优解或已选计划。无路径通往 Boss 时为 null，UNKNOWN 保留未知。第二十局第 9 层只读回放由必经精英的左分支改为存在零已知精英路线的右分支。

完整方案局部优化现在使用平衡的成对比较；同一轮的独立问题在请求容量内批量发送，每一对只比较两个互斥的完整顺序。换了基准方案后重新允许上一轮出现的候选，不再被跨轮去重排除。候选直接列能量消耗、条件生命损失、对每个敌人的生命/格挡削减；这些仍是有限算术，不能冒充完整引擎模拟。

方案逐步显示扣除预留费用后剩余的能量，避免只看整回合总耗能而忽略抽牌时机。局部候选也包含删除一个动作，用来比较省掉重复防御等无收益消耗；仍检查下一张牌依赖、实体牌不重复，以及自动出牌所保留的牌不能失去前置动作。第二十局第 12 层真实局面中，旧计划先 Defend 再 Shrug It Off，抽牌后能量为零；保留原计划、此前记忆和实际状态的只读回放改为先 Shrug It Off，抽牌后保留 1 能量。后续仍有一张拟定 Defend，抽牌后需复核，不能声称整个后续决策已最优。

完整方案比较也使用与目标/主要动作阶段相同的 `turnStrategyInstructions`，包括战斗时机、准备、消耗品、集中减员与后续回合取舍。此前这一阶段只有比较说明和回合目标，可能在最后重新偏向即时格挡。第二十局第 7 层第 2 回合的只读生产回放从 Defend → Headbutt → Defend 改为 Setup Strike → Headbutt → Defend，先利用本回合力量再攻击，保留一张防御；只使用该决策前的记忆与原始状态。回放不执行游戏动作，也不证明整场战斗胜利。

只读历史样本中，第十八局第 6 层改为 Strike → Strike → Evil Eye，条件格挡由原 Defend 的 5 提高到 8；Vantom 伤害上限回合改为 Defend → Strike → Defend。Tunneler 样本仍未找到 Bash 配合重复攻击打破护甲的更好方案。回放仅重建该日志片段内已发生的动作，不含后续事实，也不证明整局胜率提高；批量共享状态减少传输重复，问题总 token 消耗可能上升。

- 原生实时描述、升级、费用、力量/虚弱后的目标预览、遗物计数器、意图和合法动作优先。静态库明确区分基础与升级规则。
- Wiki 是社区抽取资料。原始全量响应保存在本地，但 `cards_draw` 等解析摘要不参与计算：例如 Blade Dance 的该字段为 3，而原文实际是生成 3 张 Shiv。动态能力模板缺失的金额不能猜成零。
- 事件资料为公开的可能页面；没有数据的页面明确标记缺失。怪物公开招式表与一般规律不表示本局未来随机动作。
- 原生命中次数优先，现由模组明确导出 Conflagration、Twin Strike、Whirlwind。缺失时仅解析实时牌面中无条件的第一句多段伤害；存在未解析的条件重复或 X 费时，次数保持未知，不默认一次。不模拟攻击前、命中间及死亡触发。Rage 在整张攻击之后触发一次，零次命中的攻击也可以触发；战斗结束等中断仍可能改变结果。
- 历史中出现临时敏捷使用太晚时，请求本来已有 Dexterity 的原生解释。因此规则库只能改善信息组织，不能单独证明解决了决策错误。
